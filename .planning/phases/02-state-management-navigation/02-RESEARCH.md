# Phase 2: State Management & Navigation - Research

**Researched:** 2026-02-19
**Domain:** Rust CLI fuzzy matching, shell integration, frecency algorithms, filesystem operations
**Confidence:** HIGH

## Summary

Phase 2 transforms the basic project tracker into a smart navigation tool. The core challenge is enabling shell directory changes from a compiled binary (impossible directly - requires shell wrapper functions), implementing frecency-based ranking, and providing responsive fuzzy matching. The shell integration pattern follows zoxide's proven approach: the Rust binary computes the best match and outputs the path, while a shell function performs the actual `cd` command.

The fuzzy matching domain has two solid options: `fuzzy-matcher` (0.3.7) is simpler with SkimV2 algorithm, while `nucleo` (0.5.0) from the Helix editor is higher performance but more complex. For this use case with <1000 projects, fuzzy-matcher is sufficient and simpler to integrate.

Auto-demotion requires checking filesystem modification times non-blockingly. Rust's `std::fs::metadata().modified()` provides this efficiently. The auto-discovery feature for new subdirectories can use `walkdir` for synchronous scanning or `ignore` for parallel scanning with gitignore respect.

**Primary recommendation:** Use fuzzy-matcher for matching, implement zoxide-style shell wrapper functions, store frecency scores in SQLite with the documented time-decay formula, and perform auto-demotion checks asynchronously during command execution.

### Pattern 1: Shell Wrapper Functions (zoxide pattern)
**What:** Generate shell functions that call the binary and execute `cd` on the result
**When to use:** Always - binaries cannot change shell working directory directly
**Example:**
```bash
# Generated by: activate init bash

# Change directory wrapper
__activate_cd() {
    \builtin cd -- "$@"
}

# Main activation function
activate() {
    local result
    result="$(command activate query --exclude "$(pwd)" -- "$@")" && __activate_cd "${result}"
}

# Tab completion registration
_activate_completions() {
    local cur="${COMP_WORDS[COMP_CWORD]}"
    COMPREPLY=($(command activate completions --shell bash --current "$cur"))
}
complete -F _activate_completions activate
```

### Pattern 2: Frecency Scoring
**What:** Combine frequency and recency to rank projects
**When to use:** Sorting query results by likely user intent
**Example:**
```rust
// Source: zoxide algorithm documentation
use chrono::{DateTime, Duration, Utc};

pub fn calculate_frecency(visit_count: u32, last_visit: DateTime<Utc>) -> f64 {
    let base_score = visit_count as f64;
    let now = Utc::now();
    let elapsed = now.signed_duration_since(last_visit);

    // Time decay multipliers (zoxide algorithm)
    let multiplier = if elapsed < Duration::hours(1) {
        4.0
    } else if elapsed < Duration::hours(24) {
        2.0
    } else if elapsed < Duration::weeks(1) {
        0.5
    } else {
        0.25
    };

    base_score * multiplier
}
```

### Pattern 3: Fuzzy Matching with Scoring
**What:** Use SkimMatcherV2 for fuzzy project name matching
**When to use:** All project lookups to support partial matching
**Example:**
```rust
// Source: fuzzy-matcher documentation
use fuzzy_matcher::FuzzyMatcher;
use fuzzy_matcher::skim::SkimMatcherV2;

pub struct ProjectMatcher {
    matcher: SkimMatcherV2,
}

impl ProjectMatcher {
    pub fn new() -> Self {
        Self {
            matcher: SkimMatcherV2::default(),
        }
    }

    /// Returns projects sorted by combined fuzzy + frecency score
    pub fn match_projects(&self, query: &str, projects: &[Project]) -> Vec<MatchResult> {
        let mut results: Vec<_> = projects
            .iter()
            .filter_map(|p| {
                self.matcher.fuzzy_match(&p.name, query).map(|fuzzy_score| {
                    let frecency = calculate_frecency(p.visit_count, p.last_touched);
                    MatchResult {
                        project: p.clone(),
                        fuzzy_score,
                        frecency,
                        combined_score: fuzzy_score as f64 + frecency,
                    }
                })
            })
            .collect();

        results.sort_by(|a, b| b.combined_score.partial_cmp(&a.combined_score).unwrap());
        results
    }
}
```

### Pattern 4: Non-Blocking Auto-Demotion Check
**What:** Check and demote stale projects without blocking main operation
**When to use:** During every command that touches the database
**Example:**
```rust
// Source: Rust std::fs and std::thread patterns
use std::fs;
use std::thread;
use std::time::Duration;

const INACTIVE_THRESHOLD_DAYS: u64 = 14;

pub fn trigger_demotion_check(db_path: PathBuf) {
    // Fire-and-forget background check
    thread::spawn(move || {
        if let Err(e) = perform_demotion_check(&db_path) {
            eprintln!("Warning: demotion check failed: {}", e);
        }
    });
}

fn perform_demotion_check(db_path: &Path) -> Result<()> {
    let conn = Connection::open(db_path)?;
    let threshold = Utc::now() - Duration::days(INACTIVE_THRESHOLD_DAYS);

    conn.execute(
        "UPDATE projects SET state = 'inactive', updated_at = ?1
         WHERE state = 'active' AND last_touched < ?2",
        params![Utc::now().timestamp(), threshold.timestamp()],
    )?;
    Ok(())
}
```

### Pattern 5: Create-on-Activate for Non-Existent Projects
**What:** When activating a non-existent project, offer to create it
**When to use:** When user activates a name that doesn't exist in database
**Example:**
```rust
// Interactive flow for creating new projects
pub fn activate_or_create(db: &Database, name: &str) -> Result<PathBuf> {
    // First, try to find existing project
    if let Some(project) = find_project_by_fuzzy_match(db, name)? {
        // Update last_touched and return path
        update_last_touched(db, project.id)?;
        return Ok(project.path);
    }

    // Project doesn't exist - ask user if they want to create it
    eprintln!("Project '{}' not found.", name);
    eprint!("Create it? [y/N]: ");

    let mut response = String::new();
    std::io::stdin().read_line(&mut response)?;

    if response.trim().to_lowercase() == "y" {
        // Get tracked directory from config
        let config = Config::load()?;
        let new_path = config.tracked_directory.join(name);

        // Create the directory
        std::fs::create_dir_all(&new_path)?;

        // Add to database as active
        add_project(db, name, &new_path)?;
        set_project_state(db, name, ProjectState::Active)?;

        Ok(new_path)
    } else {
        Err(anyhow::anyhow!("Project not found and creation declined"))
    }
}
```

### Anti-Patterns to Avoid
- **Direct cd from binary:** Impossible - always use shell wrapper functions
- **Blocking sync checks:** Auto-demotion should never delay user commands
- **Hard-coded shell syntax:** Use clap_complete for shell-specific completions
- **Full directory scan on every command:** Cache discovery results, scan periodically

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Fuzzy matching | Simple substring/regex | fuzzy-matcher SkimMatcherV2 | Handles typos, reordering, gaps correctly |
| Shell escaping | Quote wrapping | shell-escape crate | Handles all special chars including NUL |
| Shell completions | Bash/zsh scripts by hand | clap_complete | Tested across shell versions, handles edge cases |
| Frecency algorithm | Custom heuristic | zoxide's documented formula | Proven in production with millions of users |
| Directory traversal | Manual readdir | walkdir | Handles symlinks, permissions, errors correctly |

**Key insight:** Shell integration is surprisingly complex. Different shells have different quoting rules, completion APIs, and function syntax. Let clap_complete handle the differences.

## Common Pitfalls

### Pitfall 1: Trying to cd from Binary
**What goes wrong:** Binary runs in subprocess, cd only changes subprocess's directory
**Why it happens:** Misunderstanding of how shells and processes work
**How to avoid:** Generate shell wrapper function that calls binary, parses output, runs cd
**Warning signs:** "Nothing happens" when running activate command

### Pitfall 2: Blocking on Filesystem Stat
**What goes wrong:** Auto-demotion check stats every project file, causing slow startup
**Why it happens:** Checking modification times synchronously for all projects
**How to avoid:** Run demotion check in background thread, or check lazily per-project
**Warning signs:** Noticeable delay (>100ms) when running any command

### Pitfall 3: Shell Completion Cache Staleness
**What goes wrong:** Tab completion shows old project list after adding new projects
**Why it happens:** Shell caches completion results for performance
**How to avoid:** Use dynamic completions (clap_complete env module) that query database each time
**Warning signs:** New projects don't appear in tab completion until shell restart

### Pitfall 4: Frecency Score Overflow/Underflow
**What goes wrong:** Projects with very high visit counts dominate forever
**Why it happens:** Linear scoring with no normalization or decay
**How to avoid:** Use multiplicative decay (zoxide formula), consider periodic score normalization
**Warning signs:** Very old projects still appearing first despite not being accessed recently

### Pitfall 5: Race Condition in Auto-Discovery
**What goes wrong:** Same project added twice during parallel discovery
**Why it happens:** Discovery thread and user add command race
**How to avoid:** Use database UNIQUE constraint, handle "already exists" gracefully
**Warning signs:** Duplicate project errors during sync command

### Pitfall 6: Create-on-Activate in Non-Interactive Context
**What goes wrong:** Activation hangs waiting for stdin when called from script
**Why it happens:** Prompting for input when stdin isn't a TTY
**How to avoid:** Check `atty::is(atty::Stream::Stdin)` before prompting, use `--create` flag for scripts
**Warning signs:** Scripts hang when trying to activate non-existent projects

### Filesystem Modification Time Check
```rust
// Source: Rust std::fs documentation
use std::fs;
use std::time::SystemTime;
use chrono::{DateTime, Utc};

pub fn get_project_mtime(path: &Path) -> Result<DateTime<Utc>> {
    let metadata = fs::metadata(path)
        .context("Failed to read project metadata")?;

    let modified = metadata.modified()
        .context("Modification time not available")?;

    let duration = modified.duration_since(SystemTime::UNIX_EPOCH)
        .context("System time before UNIX epoch")?;

    DateTime::from_timestamp(duration.as_secs() as i64, 0)
        .ok_or_else(|| anyhow::anyhow!("Invalid timestamp"))
}

pub fn is_project_stale(path: &Path, threshold_days: u64) -> Result<bool> {
    let mtime = get_project_mtime(path)?;
    let threshold = Utc::now() - chrono::Duration::days(threshold_days as i64);
    Ok(mtime < threshold)
}
```

### Directory Auto-Discovery
```rust
// Source: walkdir 2.5.0 documentation
use walkdir::WalkDir;

pub fn discover_projects(tracked_dir: &Path, ignore_patterns: &[String]) -> Vec<PathBuf> {
    WalkDir::new(tracked_dir)
        .min_depth(1)  // Skip tracked_dir itself
        .max_depth(1)  // Only immediate children
        .into_iter()
        .filter_entry(|e| {
            // Skip hidden directories and ignored patterns
            let name = e.file_name().to_string_lossy();
            !name.starts_with('.') && !ignore_patterns.iter().any(|p| name.contains(p))
        })
        .filter_map(|e| e.ok())
        .filter(|e| e.file_type().is_dir())
        .map(|e| e.into_path())
        .collect()
}
```

## Open Questions

1. **Interactive vs Non-Interactive Create**
   - What we know: Create-on-activate needs to prompt user
   - What's unclear: Exact UX for non-TTY contexts
   - Recommendation: Add `--create` flag for scripts, prompt only when TTY detected

2. **Frecency Formula Tuning**
   - What we know: zoxide formula works well for directory navigation
   - What's unclear: Whether project management has different usage patterns
   - Recommendation: Start with zoxide formula, tune based on user feedback

3. **Completion Performance**
   - What we know: Dynamic completions query DB on each tab press
   - What's unclear: Latency impact with large project counts
   - Recommendation: Cache completion results for 1-2 seconds, invalidate on DB write

4. **Auto-Discovery Frequency**
   - What we know: Need to find new subdirectories in tracked folder
   - What's unclear: How often to scan (every command vs manual sync)
   - Recommendation: Scan during explicit `sync` command, not on every operation
